# link-design-pitch

**시각 방향을 고른 뒤, 실제 내용에 맞는 상세 시안과 적용 명세까지 만드는 플러그인입니다.**

> 이 플러그인은 소스 코드나 Word·Excel·PowerPoint 파일을 직접 수정하지 않습니다. 방향을 고르는
> 스킬과, 정한 방향을 화면별 상세 시안·디자인 토큰·작업 목록으로 구체화하는 스킬을 제공합니다.

마켓플레이스를 등록한 뒤 **터미널**에서 설치합니다.

```bash
claude plugin install link-design-pitch@link-skills
```

한 번 설치하면 스킬 2개가 함께 들어옵니다.

| 순서 | 호출 | 결과 | 멈추는 지점 |
|---|---|---|---|
| 1 | `link-design-pitch:link-design-pitch` | 실제 내용으로 만든 시안 10개와 추천 | 사용자가 방향을 고르기 전 |
| — | 별도 제작 단계 | 실제 기능과 내용을 만듦 | 이 플러그인의 범위가 아님 |
| 2 | `link-design-pitch:link-design-pitch-detail` | 실제 화면별 상세 시안과 적용 작업 목록 | 인터랙션 방식을 고르기 전 |

두 번째 스킬은 선택한 방향이 기록된 `DECISION.md`가 없으면 시작하지 않습니다. 실제 기능이나 내용도
먼저 만들어져 있어야 합니다. 아직 방향을 고르지 않았다면 첫 번째 스킬부터 시작하세요.

웹·데스크톱·모바일 앱뿐 아니라 발표 자료, 스프레드시트, 문서, 인쇄물에도 사용할 수 있습니다. 다만
브라우저가 아닌 산출물의 시안은 실제 파일을 수정해 만든 화면이 아니라 HTML로 표현한 근사치입니다.

---

## 전체 흐름

```text
대상과 제약 확인
  → 질문 5개
  → 29개 카탈로그에서 방향 10개 선택
  → 실제 내용으로 시안 10개 제작
  → 비교·추천
  → 사용자가 방향 선택
  → 실제 기능과 내용을 별도로 제작
  → 실제 화면별 상세 시안·측정·적용 목록
  → 필요한 경우 인터랙션 선택
```

두 스킬을 나눈 이유는 디자인을 실제 내용보다 먼저 구체화하면 필드 수, 제목 길이, 목록 행 수를
추측하게 되기 때문입니다. 방향을 먼저 고르고 실제 기능과 내용을 만든 뒤 상세 시안을 만들어야
재작업을 줄일 수 있습니다.

## 스킬 1 — 방향 고르기

### 언제 쓰나

- 새 앱·문서·발표 자료의 시각 방향이 정해지지 않았을 때
- 기존 결과물이 밋밋하거나 낡아 보여 새 테마를 비교하고 싶을 때
- 디자인 용어를 모르지만 눈으로 후보를 비교하고 싶을 때
- 색, 글꼴, 여백이 제각각인 여러 산출물을 하나의 체계로 맞추고 싶을 때

간단한 문구나 파일 하나의 색만 고치는 일에는 맞지 않습니다. 시안 10개를 실제 내용으로 만들고
검증하는 큰 작업을 시작할 때 사용하는 스킬입니다.

### 시작 전에 확인하는 것

먼저 대상 환경에서 실제로 표현할 수 있는 효과를 확인합니다. 제약은 “데스크톱 앱”처럼 넓은 종류가
아니라 사용하는 기술을 기준으로 판단합니다.

- Qt 스타일시트는 `box-shadow`와 `backdrop-filter`를 지원하지 않습니다.
- 일부 이메일 클라이언트는 Flexbox·Grid 지원이 제한됩니다.
- 인쇄물에는 화면의 다크 모드와 같은 개념이 없습니다.

이미 만들어진 결과물이 있다면 구조를 얼마나 바꿀 수 있는지와 테마 교체 비용도 먼저 확인합니다.
지원 여부가 불확실한 효과는 작은 예제로 렌더해 검증한 뒤 후보에 넣습니다.

### 질문 다섯 개

질문은 한 번에 묻습니다.

1. **누구를 위한 것인가** — 고객, 상급자, 동료, 매일 쓰는 실무자처럼 실제 독자를 확인합니다.
2. **무엇을 만드는가** — 웹 대시보드, PowerPoint 발표 자료, Excel 보고서처럼 산출물 형식을
   확인합니다.
3. **핵심 색은 무엇인가** — 선호 색이나 회사 표준 색을 받습니다. 정하지 못했다면 팔레트 4개를
   제안합니다.
4. **레이아웃은 어떻게 나누는가** — 좌측 메뉴와 본문, 카드 격자, 세로 흐름, 좌우 분할 등의
   선택지와 장단점을 제시합니다.
5. **유도할 단 하나의 행동은 무엇인가** — “예산안을 검토하게 한다”보다 “3안이 아니라 2안으로
   결정하게 한다”처럼 결과의 방향까지 확인합니다.

마지막 답은 화면에서 무엇을 가장 크게, 진하게, 먼저 보이게 할지를 정합니다.

### 시안 10개

29개 시각 방향이 담긴 카탈로그에서 현재 작업에 맞는 10개를 고릅니다. 29개를 모두 보여주는 것은
아닙니다.

- 잘 맞는 방향 3~4개
- 인접한 후보 2~3개
- 탈락할 가능성이 높지만 제약을 드러내는 후보 최소 2개

모든 시안은 같은 크기와 구조에 실제 제목·수치·항목을 넣어 만듭니다. 서로 다른 방향의 차이만
비교할 수 있게 하기 위해서입니다. 브라우저가 아닌 산출물의 경우, 보드에 실제 화면의 캡처가 아니라
렌더링 근사치라는 점을 표시합니다.

### 비교하고 추천한 뒤 멈춤

열 방향을 다음 기준으로 비교합니다.

- 어떤 목적에 강한가
- 무엇을 포기해야 하는가
- 대상 환경에서 실제로 만들 수 있는가

그중 하나 또는 두 방향의 조합을 추천하고, 추천에 대한 가장 강한 반론도 함께 적습니다. 이후 어느
방향을 선택할지 묻고 멈춥니다. 방향을 대신 결정하거나 상세 화면을 미리 만들지 않습니다.

## 스킬 2 — 선택한 방향 구체화

### 시작 조건

다음 두 조건을 모두 만족해야 합니다.

1. `DECISION.md`에 선택한 방향이 기록돼 있습니다.
2. 실제 기능이나 내용이 만들어져 있습니다.

기록이 예상 위치에 없으면 프로젝트 전체에서 찾고, 그래도 찾지 못하면 사용자에게 위치를 묻습니다.
선택한 방향을 확인할 수 없을 때는 임의로 정하지 않고 첫 번째 스킬로 돌아갑니다.

### 실제 화면별 상세 시안과 적용 목록

한 화면에서 잘 맞던 방향이 다른 화면의 실제 내용에서는 무너질 수 있으므로 서로 다른 실제 화면을
빠짐없이 다룹니다. 탭이 4개인 앱이라면 4개 화면을 확인합니다. 발표 자료는 실제로 다른 슬라이드
레이아웃을, 스프레드시트는 서로 다른 시트 유형을 봅니다.

각 유형에서 다음을 확인합니다.

- 가장 중요한 요소가 의도한 방식으로 눈에 띄는가
- 글자 대비가 4.5:1 기준을 만족하는가
- 색·글꼴·간격 값인 디자인 토큰이 모두 기록돼 있는가
- 코드 프로젝트라면 하드코딩된 색과 수정할 파일·줄이 어디인가

결과는 상세 HTML·PNG 시안과 구현 작업 목록입니다. 실제 소스 코드나 문서 파일을 수정하지는
않습니다.

### 인터랙션 선택지

발표 자료·스프레드시트·인쇄물처럼 움직이지 않는 산출물에서는 이 단계를 건너뜁니다.

사람이 조작하는 결과물이라면 실제로 영향을 주는 갈림길 2~3개만 고릅니다. 예를 들면 다음과
같습니다.

- 저장 버튼을 눌러야 반영할지, 바꾸는 즉시 반영할지
- 삭제 전에 확인할지, 먼저 지우고 되돌리기를 제공할지
- 상세 내용을 새 창에 띄울지, 현재 화면 옆에 붙일지

선택지·장단점·추천을 제시하고 사용자가 고를 때까지 멈춥니다. 상태별 화면이나 동작을 실제로
구현하지 않습니다.

## 만들어지는 파일

프로젝트가 문서를 두는 위치를 찾습니다. `docs/`가 있으면 `docs/design/`, 없으면 루트의 `design/`을
사용하며, 폴더가 없으면 새로 만듭니다.

| 파일 | 만드는 스킬 | 내용 |
|---|---|---|
| `01-directions.html` | 스킬 1 | 실제 내용으로 만든 시안 10개 |
| `01-directions.png` | 스킬 1 | HTML을 열 수 없는 곳에서 보는 같은 보드 |
| `02-detail-<방향>.html` · `.png` | 스킬 2 | 실제 화면별 상세 시안 |
| `DECISION.md` | 둘 다 | 답변, 비교, 추천과 선택, 측정값, 토큰, 인터랙션 선택, 적용 목록 |

`DECISION.md`는 두 스킬을 잇는 기록입니다. 두 번째 스킬은 이 파일을 읽고 시작하며, 다음 세션이나
다른 에이전트도 같은 결정을 재현할 수 있습니다.

## 하지 않는 것

- 대상 환경이 구현할 수 없는 효과를 확인 없이 제안하지 않습니다.
- 과거 선택을 기억해 다음 시안의 범위를 줄이지 않습니다.
- 사용자를 대신해 디자인 방향을 결정하지 않습니다.
- 실제 코드나 Word·Excel·PowerPoint 파일을 수정하지 않습니다.
- 인터랙션 선택을 받기 전에 상태별 화면과 동작을 만들지 않습니다.
