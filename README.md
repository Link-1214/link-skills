# link-skills

**AI와 일하면서, 판단은 내가 쥡니다.**

AI로 일하다 "이건 절차로 굳혀두는 게 낫겠다" 싶은 것들을 스킬로 만들어 모은 저장소입니다.

AI는 선택지를 펼치고, 근거를 대고, 실행하는 데 강합니다. 다만 **핸들은 그 일을 아는 사람이
쥐어야 합니다.** AI가 대신 결정해 버리면 두 가지를 잃습니다.

**고르지 않았을 길을 볼 기회.** 답 하나만 받으면 판단이 매번 AI에게 넘어갑니다. 다른 길을 같이
봐야 무엇이 왜 나은지 스스로 따져 볼 수 있고, 그래야 다음 결정이 더 나아집니다.

**왜 이 길로 왔는지 설명할 근거.** 결정한 이유를 모르면 그다음 지시가 흐려집니다. 지시가
흐려지면 프로젝트는 방향을 잃습니다.

그래서 여기 스킬은 전부 같은 성질을 갖습니다. **판단이 필요한 지점에서 멈추고 묻습니다.**
그리고 무엇을 왜 정했는지 파일로 남깁니다.

멈추는 곳은 스킬마다 다릅니다. 디자인 스킬은 방향을 고르기 전에, 스킬 작성 기준은 그 스킬이
무엇을 약속할지 정하기 전에 멈춥니다. 공통점은 **사실과 판정은 알아서 하고, 약속과 방향만
사람에게 묻는다**는 것입니다. 되돌리기 쉬운 일까지 매번 물으면 그건 도구가 아니라 설문입니다.

## 플러그인이 처음이라면

Claude Code를 확장하는 방식입니다. 세 단계로 되어 있습니다.

| | 무엇 | 하는 일 |
|---|---|---|
| **마켓플레이스** | 저장소 | 한 번 등록해 두는 목록. 이 저장소가 그것입니다 |
| **플러그인** | 설치 단위 | 목록에서 골라 설치합니다. 스킬 여러 개를 담습니다 |
| **스킬** | 호출 단위 | 실제로 부르는 것. `link-design-pitch:link-design-pitch` |

설치한 스킬은 대화 중에 이름으로 부르거나, 상황이 맞으면 AI가 알아서 씁니다. 다만 비슷한 디자인
스킬이 여럿 설치돼 있으면 "더 예쁘게 해줘" 같은 요청이 어느 스킬로 갈지는 보장되지 않습니다.
확실히 부르려면 이름으로 부르세요 — "link-design-pitch 실행해줘".

설치는 플러그인 단위입니다. 한 플러그인 안의 스킬은 따로 받을 수 없습니다. 서로 없으면 의미가
없는 스킬은 그래서 한 플러그인으로 묶습니다.

## 스킬 목록

### link-design-pitch

**시각 방향을 고르고, 정해진 뒤 실제 화면에 적용합니다.** 스킬 2개.

```bash
claude plugin install link-design-pitch@link-skills
```

| 순서 | 호출 | 하는 일 |
|---|---|---|
| 1 | `link-design-pitch:link-design-pitch` | 질문 5개 → 시안 10개 → 추천 → **멈추고 선택을 물음** |
| — | *직접 만드는 단계* | 실제 기능과 내용을 만듭니다 |
| 2 | `link-design-pitch:link-design-pitch-detail` | 정해진 방향을 모든 화면에 적용 → 인터랙션 선택지 제시 |

**어디에 쓰나.** 웹·데스크톱 앱, 모바일 앱, 그리고 Word·Excel·PowerPoint 문서까지.

**왜 둘로 나뉘어 있나.** AI와 작업하다 보면 방향을 정한 뒤에 **실제로 만드는 단계**가 옵니다.
전체 테마를 먼저 잡고, 그에 맞춰 기능과 내용을 만들고, 그다음 디자인 통일성을 맞추는 순서입니다.
한 번에 하려고 하면 아직 없는 화면을 AI가 상상해서 그리는데, 목록이 몇 줄인지 제목이 얼마나 긴지는
만들어 봐야 알기 때문에 대부분 다시 그리게 됩니다.

#### 이 스킬이 해결하는 것

**디자인 도메인 지식이 없어도 됩니다.** "글래스모피즘으로 해줘"라고 요청하려면 그 단어를 먼저
알아야 합니다. 용어를 모르면 원하는 걸 설명할 방법 자체가 없습니다. 이 스킬은 29가지 시각 방향을
**당신이 요청한 내용을 기반으로 렌더해서** 보여줍니다. 전문 용어는 몰라도 괜찮습니다. 눈으로
고르세요.

**산출물이 달라도 톤앤매너가 하나로 갑니다.** 발표 자료·대시보드·보고서를 각각 만들면 색과 글꼴과
여백이 제각각이 됩니다. 한 번 정한 방향을 토큰 값까지 기록으로 남겨 두면, 다음에 무엇을 만들든
같은 디자인 시스템 위에서 시작합니다.

#### 무엇이 나오나

프로젝트가 문서를 두는 곳에 만들어집니다. `docs/` 가 있으면 `docs/design/`, 없으면 `design/`.
**해당 폴더가 없으면 새로 만듭니다.**

| 파일 | 내용 |
|---|---|
| `01-directions.html` · `.png` | 시안 10개 보드. HTML은 브라우저용, PNG는 GitHub·메신저처럼 HTML이 안 열리는 곳용 |
| `02-detail-<방향>.html` · `.png` | 선택한 방향을 적용한 모든 화면 |
| `DECISION.md` | 답변·판정·측정값·색상 토큰. 다음 세션과 다른 AI가 읽는 기록 |

### link-skill-authoring

**스킬이 무엇을 보장해야 하는지 정하는 기준입니다.** 스킬 1개.

```bash
claude plugin install link-skill-authoring@link-skills
```

| 호출 | 하는 일 |
|---|---|
| `link-skill-authoring:link-skill-authoring` | 스킬을 만들거나 고치거나 검토할 때 기준을 댐 |

**어디에 쓰나.** 스킬을 새로 만들 때, 있는 스킬을 고칠 때, 남이 만든 스킬을 검토할 때. 스킬이
엉뚱할 때 뜨거나 떠야 할 때 안 뜨는 경우에도 씁니다.

**이 스킬이 해결하는 것.** 스킬을 만들 때마다 무엇을 잘 만든 것으로 볼지 다시 정하면 저장소가
중구난방이 됩니다. 그렇다고 긴 체크리스트를 만들면 안 맞는 항목을 억지로 채우게 됩니다. 감사하는
스킬과 시안을 펼치는 스킬은 잘 만든 모습이 다르기 때문입니다.

그래서 공통 규칙을 둘로 줄였습니다. 기준은 하나입니다 — **어겼을 때 조용히 실패하는가.** 헷갈리게
쓰였거나 느린 스킬은 쓰다 보면 저절로 드러나므로 규칙이 필요 없습니다. 규칙이 값을 하는 자리는
틀렸는데 아무도 모르는 쪽뿐입니다.

| 층 | 내용 | 적용 |
|---|---|---|
| **규칙 둘** | 필요할 때 뜬다. 모를 때 추측을 숨기지 않는다 | 모든 스킬, 예외 없음 |
| 계약 한 줄 | 그 스킬이 무엇을 약속하는지 `SKILL.md` 에 한 줄 | 약속할 경계가 있을 때만 |
| 질문 여섯 | 만들기 전에 답해 봄 | 「해당 없음」도 답 |

두 층을 섞지 않는 것이 핵심입니다. 참조 자료만 담은 스킬에 계약 한 줄을 억지로 붙이면, 이 스킬이
막으려던 일을 이 스킬이 하게 됩니다.

**어디서 멈추나.** frontmatter 필드가 실재하는지, BOM이 붙었는지, description에 절차가 섞였는지 —
이런 사실과 판정은 묻지 않고 확인해서 고칩니다. **멈추는 곳은 한 군데입니다. 그 스킬이 무엇을
약속할지 정할 때.** 계약과 경계는 만드는 사람만 답할 수 있고, 대신 써주면 나중에 "왜 이렇게
정했나"에 대한 답이 "AI가 정했습니다"가 됩니다.

**무엇이 나오나.** 별도 파일을 만들지 않습니다. 결정은 `SKILL.md` 의 계약 한 줄로 남습니다 —
약속이 지켜지는 자리에 그대로 적히는 셈입니다.

**`skill-creator` 를 대신하지 않습니다.** 그쪽이 초안·테스트·평가 절차를 맡고, 이 스킬은 그
절차가 겨냥할 기준을 댑니다. 다만 실제로 확인해 보니 둘이 같이 뜨지는 않아서, 만들거나 고치는
중이면 이 스킬이 그쪽을 직접 불러 줍니다.

### link-skill-packer

**만든 스킬을 깃 없이 남에게 넘깁니다.** 스킬 1개. 파이썬이 필요합니다.

```bash
claude plugin install link-skill-packer@link-skills
```

| 호출 | 하는 일 |
|---|---|
| `link-skill-packer:link-skill-packer` | 스킬 폴더를 검사한 뒤 zip 하나로 묶음 |

**어디에 쓰나.** 회사에서 깃허브가 막혀 있을 때 씁니다. 공유 드라이브든 메일이든, 파일 하나를
건네줄 수만 있으면 됩니다.

받는 사람도 씁니다. 「깔았는데 목록에 안 떠」일 때 이 스킬이 원인을 찾아 줍니다. 그럴 때는 포장하지
않고 검사만 한 뒤 멈춥니다. 스킬이 **뜨긴 뜨는데 엉뚱한 때 뜬다면** 그건 설명문 문제라
`link-skill-authoring` 이 다룹니다.

**이 스킬이 해결하는 것.** 스킬은 원래 깃 저장소에 올려 플러그인으로 배포합니다. 회사에서 그 길이
막히면 바로 옆자리 사람에게도 스킬을 못 줍니다.

그런데 zip으로 묶는 것만 놓고 보면 명령 한 줄이라, 그것 때문에 스킬까지 만들 일은 아닙니다.
만든 이유는 따로 있습니다.

**받은 스킬은 조용히 고장 납니다.** 에러가 안 납니다. 목록에 그냥 없습니다. 받은 사람은
「안 되는데요」 말고 할 말이 없고, 준 사람도 어디를 봐야 할지 모릅니다. 그런데 보내기 전에 검사하면
몇 초 만에 잡힙니다.

패커가 막는 항목은 전부 그 부류입니다.

| 패커가 막는 것 | 그냥 두면 |
|---|---|
| `SKILL.md` 가 없다 | 스킬 폴더가 아닙니다 |
| `SKILL.md` 맨 앞에 BOM이 붙었다 | 설정이 통째로 무시돼 목록에 안 뜹니다 |
| frontmatter 블록이 없다 | 위와 같습니다 |
| `description` 이 없다 | 모델이 스킬을 부를 근거가 없어 안 뜹니다 |
| `description` 안에 콜론+공백이 있다 (따옴표 없이) | YAML이 다른 뜻으로 읽고 설정을 버립니다 |

다섯 가지뿐입니다. 파일만 열어 보면 참인지 거짓인지 바로 나오는 것들이라 막아도 안전합니다.

이 다섯으로 좁힌 이유가 있습니다. 이 컴퓨터에 깔린 스킬 81개를 패커로 검사해 봤더니, 기준이 조금만
넓어도 **정상인 스킬 13개가 걸렸습니다.** 그래서 애매한 검사는 전부 경고로 내렸습니다.

**패커가 막지 않고 보여만 주는 것**도 있습니다. 절대경로, 폴더 밖을 가리키는 링크, 비밀번호처럼
보이는 문자열, 사설 IP, 이메일 주소입니다. 문서에 적어 둔 예시일 수도 있고 진짜일 수도 있는데, 그
둘은 기계가 못 가립니다. 그래서 패커는 「절대경로 발견」이라고 하지 않고 「예시입니까, 스킬이 실제로
여는 경로입니까」라고 묻습니다.

**패커가 대신 고쳐 주지는 않습니다.** 보내는 길에 남의 스킬에 손대면, 만든 사람이 시험한 것과 받는
사람이 받는 것이 달라집니다.

**어디서 멈추나.** 한 번입니다. 「이 스킬 맞습니까?」

패커는 파일 목록을 다 늘어놓지 않습니다. 열네 줄을 보여줘도 사람은 안 읽고, 읽어도
`references/guide.md` 가 위험한지는 이름만 봐선 모릅니다. 평범한 파일은 개수만 세고, 튀는 것만
이유를 붙여 보여줍니다.

```
6 of these look like ordinary skill material — assets/ 1, folder root 2, references/ 2, scripts/ 1

These do not, and placing them is the part no scan can do:
  references/고객명단.md      16 B   nothing in the skill links to it
  실적_2026Q2.xlsx           16 B   a data file rather than skill material
  작업중/메모.txt              20 B   the name reads like a draft or a personal copy
```

이 컴퓨터의 스킬 81개를 패커로 검사해 보니 **72개는 이름과 파일 개수만 나왔습니다.** 패커가 없는
것을 억지로 채워 넣지 않기 때문입니다. 전체 목록을 보고 싶으면 `--all` 을 붙이면 됩니다.

파일이나 설정 등을 제외해야 한다면 폴더에서 지우고 다시 돌려야 합니다. **일부만 골라 담을 수는
없습니다.** 그런 기능이 있다면 주는 사람과 받는 사람이 서로 다른 것을 갖게 되고, 결국 다른 스킬이
됩니다.

**무엇이 나오나.** `<스킬이름>-skill.zip` 하나입니다. 안에 스킬 폴더와 `INSTALL.md` 가 들어 있고,
받는 사람은 폴더 하나를 복사하면 끝납니다. 받는 사람에게 이 스킬은 필요 없습니다.

`INSTALL.md` 에는 받는 사람이 혼자서는 알아낼 수 없는 것을 적습니다.

- **먼저 깔려 있어야 하는 것** — 파이썬이나 Node.js 같은 실행기, 그리고 `.py` 가 쓰는 외부 패키지
  이름입니다. zip에 담을 수 없는 것이라 이름이라도 적어 둡니다
- **파일별 SHA-256** — 받는 사람이 복사가 제대로 됐는지 직접 확인할 수 있게 합니다. 파일을 다시
  저장하면 값이 달라지고, 그 자리에서 드러납니다
- **조용히 실패하는 세 가지** — 깐 세션에서는 안 보인다는 것, 압축 풀 때 생긴 바깥 폴더를
  복사하면 안 된다는 것, 파일을 다시 쓰면 안 된다는 것

## 설치

### 이 저장소의 스킬을 전부 설치

마켓플레이스를 등록하고 `link` 를 설치합니다.

```bash
claude plugin marketplace add Link-1214/link-skills
```

```bash
claude plugin install link@link-skills
```

`link` 는 스킬이 없는 플러그인입니다. 나머지 플러그인을 의존성으로 가리키기만 합니다. 그래서 한 번
설치하면 전부 들어오고, 이 저장소에 새 스킬이 추가되면 아래 명령으로 받을 수 있습니다.

```bash
claude plugin update link@link-skills
```

### 원하는 스킬만 설치

```bash
claude plugin install link-design-pitch@link-skills
```

```bash
claude plugin install link-skill-authoring@link-skills
```


### 설치 범위

기본은 사용자 범위라 모든 프로젝트에서 쓸 수 있습니다. 팀 저장소에 함께 커밋하려면
`--scope project`, 내 작업 폴더에만 두려면 `--scope local` 을 붙입니다.

### Codex 등 다른 AI

스킬은 Claude 전용 도구를 하나도 쓰지 않는 평범한 마크다운 문서입니다. **설치할 것이 없습니다.**
저장소를 받아서 경로만 알려주면 됩니다.

```bash
git clone https://github.com/Link-1214/link-skills.git
```

그다음 AI에게 이렇게 말하면 됩니다.

```
디자인 방향을 정해야 해.
<받은경로>/link-skills/plugins/link-design-pitch/skills/link-design-pitch/SKILL.md
읽고 그대로 진행해줘.
```

매번 경로를 적기 번거로우면 프로젝트의 `AGENTS.md` 에 한 번 적어 둡니다.

```markdown
시각 방향이 안 정해졌다면
<받은경로>/link-skills/plugins/link-design-pitch/skills/link-design-pitch/SKILL.md 를 따른다

방향이 정해졌고 실제로 만들어졌다면
<받은경로>/link-skills/plugins/link-design-pitch/skills/link-design-pitch-detail/SKILL.md 를 따른다

스킬을 새로 만들거나 검토한다면
<받은경로>/link-skills/plugins/link-skill-authoring/skills/link-skill-authoring/SKILL.md 를 따른다

만든 스킬을 깃 없이 남에게 넘겨야 한다면
<받은경로>/link-skills/plugins/link-skill-packer/skills/link-skill-packer/SKILL.md 를 따른다
```

저장소의 [`AGENTS.md`](AGENTS.md) 에 AI가 읽을 안내가 정리돼 있습니다.
갱신은 받아 둔 폴더에서 `git pull` 하면 됩니다.

## 어떻게 설계했는가

당신이 무엇을 설치하는지 판단하려면 알아야 하는 내용이라 적어 둡니다.

**규칙마다 이유를 함께 적습니다.** 체크리스트나 요약만 적어 두면, 거기 없는 상황을 만났을 때
AI가 멈추거나 엉뚱하게 처리합니다. 왜 그래야 하는지를 알면 예상 못 한 경우도 판단할 수 있습니다.
유난히 구체적인 규칙이 있다면, 그건 그게 없어서 실제로 뭔가 잘못됐던 흔적입니다.

**참조 문서는 필요할 때만 읽습니다.** 항상 읽는 건 `SKILL.md` 하나입니다. 분량이 있는 문서는
앞에 색인을 두어, 전부가 아니라 그때 필요한 부분만 줄 범위로 읽습니다. 이것만으로 한 번 실행에
드는 **읽기 토큰이 29% 줄었습니다.**

다만 저 숫자는 읽기 비용만 센 것입니다. 실행 전체는 시안 열 개를 실제 내용으로 그리고 검증까지
하는 작업이라 읽기의 몇 배가 듭니다. 이 스킬은 가볍게 자주 도는 스킬이 아니라, **큰 작업을
시작하기 전에 한 번 돌아서 이후의 재작업을 없애는** 스킬입니다. 파일 하나 고치는 일에는 쓰지
마세요.

**결정할 것이 나오면 멈추고 물어봅니다.** 예를 들어 시안 10개를 보여준 다음, 어느 것으로 갈지
묻지 않고 곧장 상세 화면까지 만들어 버린다고 해 봅시다. 당신이 다른 걸 골랐다면 그 작업은 통째로
버려집니다. 더 중요한 손실은 따로 있습니다. 고르는 일을 AI가 대신해 버린 셈이 됩니다.

**특정 AI 전용 기능에 기대지 않습니다.** 그 AI에 더 나은 수단이 있으면 쓰고, 없으면 없는 대로
동작합니다. Codex 같은 다른 AI가 설치 없이 그냥 받아서 쓸 수 있는 이유입니다.

**바꾸는 이유는 실사용에서만 나옵니다.** 실제 작업에서 스킬이 깨졌을 때만 고칩니다.
좋아 보여서 미리 넣어 둔 기능은 없습니다.

새 스킬을 만드는 방법은 [`AUTHORING.md`](AUTHORING.md) 에 있습니다.

## 운영 방식

**개인 도구를 공개한 것입니다.** 제가 하는 일에 맞춰 만들었습니다. 그래서 의견이 뚜렷하고, 같은
이유로 안 맞을 수도 있습니다. 돌리기 전에 읽어 보시길 권합니다.

**버전은 직접 올립니다.** 릴리스할 때만 바뀝니다. 고침은 patch, 새 동작은 minor, 호출 이름이나
산출물 형식이 바뀌면 major 입니다. [`CHANGELOG.md`](CHANGELOG.md)

**이슈와 PR은 환영합니다. 다만 답장을 약속하지는 못합니다.** 무엇을 돌렸고 무엇이 일어났는지 적힌
버그 제보는 특히 도움이 됩니다. 기능 요청은 제가 그 필요를 직접 겪지 않으면 만들지 않을 가능성이
큽니다. 포크는 자유롭게 하셔도 됩니다.

**외부로 아무것도 보내지 않습니다.** 스킬은 지시문일 뿐입니다. 외부 서비스를 호출하지 않고,
수집하지 않고, 전송하지 않습니다.

## 문서 언어

사람이 읽는 문서는 한국어입니다.

`SKILL.md` 와 `references/` 는 영어입니다. 그 파일을 읽는 건 사람이 아니라 AI 모델이고, 같은
내용이라도 영어일 때 토큰을 덜 쓰기 때문입니다. **출력은 영어로 나오지 않습니다.** 스킬 안에
"사용자가 쓰는 언어로 답하라"가 들어 있어서, 한국어로 물으면 한국어로 답합니다.
