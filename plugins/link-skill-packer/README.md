# link-skill-packer

깃허브를 쓸 수 없는 곳에서, 직접 만든 스킬을 옆자리 동료에게 넘기기 위한 스킬입니다.

```
/plugin marketplace add Link-1214/link-skills
/plugin install link-skill-packer@link-skills
```

## 무엇을 하는지

스킬 폴더 하나를 zip으로 묶습니다. 받는 사람은 폴더 하나를 복사하면 설치가 끝납니다.

zip을 만들기 전에 검사를 겁니다. 이 스킬의 값어치는 압축이 아니라 그 검사에 있습니다.

## 어디에 쓰나

스킬은 원래 깃 저장소에 올린 플러그인으로 배포합니다. 사내에서 깃허브가 막혀 있으면 그 경로가
통째로 사라지고, 한 사람이 만든 스킬이 바로 옆 사람에게도 못 갑니다. 공유 드라이브, 메일,
메신저 첨부처럼 파일 하나를 옮길 수 있는 수단만 있으면 이 스킬로 넘길 수 있습니다.

**받는 쪽에서도 씁니다.** 「복사해서 받았는데 목록에 안 뜬다」일 때 원인을 짚습니다. 그때는 포장을
안 하고 검사만 돌린 뒤 멈춥니다 — 아무도 배달을 요청하지 않았으니까요. 흔한 원인은 셋인데 그중
하나만 파일에 있습니다.

| 원인 | 어떻게 확인하나 |
|---|---|
| BOM이나 frontmatter 파손 | `check`가 잡습니다 |
| 설치한 그 세션에서 봤음 | 스킬 목록은 세션 시작 때 읽힙니다. 새 세션에서 보면 있습니다 |
| 폴더가 한 겹 깊음 | `SKILL.md`가 `skills\<이름>\` 바로 아래 있는지 봅니다 |

세 번째는 압축을 풀면 zip 이름 폴더가 하나 더 생기는데 그 바깥 것을 복사해서 생깁니다. 흔합니다.

스킬이 **뜨긴 뜨는데 엉뚱할 때**는 이 스킬이 아닙니다. 그건 설명문 문제라
[`link-skill-authoring`](../link-skill-authoring/README.md) 몫입니다.

## 이 스킬이 해결하는 것

받는 사람 쪽에서 스킬이 고장 나는 방식에는 **오류 메시지가 없는** 것들이 있습니다. 스킬이 그냥
목록에 안 뜨고, 받은 사람은 「안 되는데요」라고만 말할 수 있습니다. 보내는 쪽에서는 몇 초면
잡히고, 받는 쪽에서는 원인을 찾기 어렵습니다.

차단하는 항목은 전부 이 부류입니다.

| 검사 | 놓치면 |
|---|---|
| `SKILL.md` 없음 | 스킬 폴더가 아닙니다 |
| `SKILL.md` 맨 앞의 BOM | 설정이 통째로 무시되고 스킬이 안 뜹니다 |
| frontmatter 블록 없음 | 같은 결과입니다 |
| `description` 없음 | 모델이 판단할 근거가 없어 발동하지 않습니다 |
| 따옴표 없는 `description`에 든 콜론+공백 | YAML이 매핑으로 읽고 설정 전체를 버립니다 |

전부 파일만 보고 확실히 판정되는 것들입니다. 그게 차단의 기준입니다. **원래 여기 있다가 빠진
검사가 둘 있습니다.** 이 컴퓨터에 깔린 스킬 81개에 돌려보고 틀린 것이 드러났습니다. `name`이
폴더명과 달라도 스킬은 **정상 로딩됩니다** — 그런 스킬 5개가 지금 목록에 떠 있고, 호출 이름은
폴더명입니다. 그리고 「참조 파일 없음」은 멀쩡한 스킬 13개를 막았습니다. 스킬 문서는 자기 번들만큼
사용자 프로젝트 얘기를 하니까요. 둘 다 지금은 질문입니다.

막지는 않고 **확인할 때 같이 보여주는** 항목이 있습니다. 절대경로, 폴더 밖을 가리키는 링크,
비밀번호처럼 보이는 문자열, 사설 IP, 이메일 주소, 그리고 한 문서 안에서 어떤 경로는 풀리는데 어떤
건 안 풀리는 경우입니다. 정당한 경우가 있어서 기계가 가릴 수 없고, 무엇이 애매한지를 함께 냅니다 —
「절대경로 발견」이 아니라 「문서 안의 예시인지, 스킬이 실제로 여는 경로인지」로 적습니다.

**참고 사항으로만 나가는 것도 있습니다.** 함께 담기는 실행 스크립트, 외부 의존성, `name` 불일치,
그리고 한 문서의 경로가 **전부** 안 풀리는 경우입니다. 판정 기준은 하나 — 그걸 보고 사용자의 답이
달라질 수 있는가. `name` 불일치는 어차피 폴더명으로 포장하니 답이 뭐든 zip이 같고, 경로가 전부 안
풀리는 문서는 사용자 프로젝트를 설명하는 문서라 81개 중 22건이 전부 그랬습니다. 답을 못 바꾸는
것을 확인 화면에 채워 넣으면, 정작 봐야 할 줄을 못 보게 됩니다.

**발견한 문제를 대신 고쳐 주지는 않습니다.** 보내는 길에 남의 스킬을 손보면, 만든 사람이 시험한
것과 실제로 나간 것이 달라집니다.

## 단계별로 어떻게 도는지

두 단계입니다.

**1. 어떤 스킬을 포장할지 확인합니다.** 폴더를 찾아 검사를 돌리고, 대상 이름과 함께 눈에 걸리는
것을 보여준 뒤 한 번 묻습니다. 이 단계에서는 아무것도 만들지 않습니다.

```
Packing `고객관리` — 12 files, 84 KB.
실적_2026Q2.xlsx 는 스킬 파일이 아니라 데이터 파일입니다.
진행할까요?
```

**2. 답을 받으면 zip을 씁니다.** 뺄 파일이 있었다면 폴더에서 지우고 1번부터 다시 합니다.

멈추는 자리는 여기 하나뿐이고, 묻는 것도 하나입니다 — **이 스킬이 맞습니까.** 판단할 목록을
따로 내밀지 않습니다. 포장은 정답이 있는 일이고 그 정답은 스크립트가 찾습니다. 기계가 진짜로 모르는
것은 「이 파일이 나가면 안 되는가」 하나인데, 대상을 내용과 함께 이름 부르면 그 자리에서 드러납니다.

### 파일 목록을 전부 보여주지 않습니다

열네 줄을 늘어놓으면 아무도 안 읽고, 읽어도 `references/guide.md` 가 위험한지는 이름만으로 모릅니다.
판단을 사람에게 떠넘긴 셈이죠. 통상적인 것은 세기만 하고 **틀에서 벗어난 것만 이유와 함께** 냅니다.

```
6 of these look like ordinary skill material — assets/ 1, folder root 2, references/ 2, scripts/ 1

These do not, and placing them is the part no scan can do:
  references/고객명단.md      16 B   nothing in the skill links to it
  실적_2026Q2.xlsx           16 B   a data file rather than skill material
  작업중/메모.txt              20 B   the name reads like a draft or a personal copy
```

무엇이 튀는가는 넷입니다 — 데이터 파일(`.xlsx`, `.csv`, `.zip`, `.pdf` 등), 초안·임시·사본처럼
읽히는 이름, 스킬치고 큰 파일, 그리고 **`references/` 안에서 아무도 링크하지 않는 마크다운.**
마지막 것이 값어치가 큽니다. 마크다운은 `SKILL.md` 에서 도달하게 되어 있으니, 아무도 안 가리키는
마크다운이 곧 흘러든 파일의 모양입니다.

**파일이 어디 놓였는지는 보지 않습니다.** 「최상위에 떠 있음」과 「스킬 구조에 없는 폴더」 두 규칙이
원래 있었는데, 설치된 스킬 81개에서 137건 중 136건을 이 둘이 만들었습니다. 한 스킬에서만 49건이
나왔고요. 그건 「이 파일이 나가면 안 된다」가 아니라 「이 사람이 내가 가정한 폴더 구조를 안 썼다」를
재고 있었습니다. 규칙을 지운 뒤 81개 전체에서 1건으로 줄었고, 시험용 위험 파일 4개는 그대로
잡힙니다.

**대개는 보여줄 것도 없습니다.** 81개 중 72개는 이름과 개수만 나옵니다. 채워 넣지 않습니다.
전체 목록을 보고 싶으면 `--all` 이 있습니다.

## 무엇이 나오나

```
<스킬이름>-skill.zip
├── INSTALL.md          무엇인지, 어떻게 설치하는지, 무엇이 담겼는지
└── <스킬이름>/          이 폴더를 통째로 복사하면 설치 끝
```

`INSTALL.md`에는 받는 사람이 스스로 알 수 없는 셋이 들어갑니다.

- **먼저 설치돼 있어야 하는 것.** 담긴 스크립트가 요구하는 실행기(파이썬, PowerShell, bash,
  Node.js)를 적고, `.py`는 import까지 읽어서 표준 라이브러리가 아닌 것을 이름으로 남깁니다.
  `pandas`를 쓰는 스킬은 파일이 다 들어 있어도 그게 없는 컴퓨터에서는 죽습니다. zip에 담을 수
  없는 부분이라 이름이라도 남기는 겁니다. import 스캔은 파이썬만 봅니다 — `.js`는 Node가
  필요하다고만 적히고 npm 패키지는 못 읽습니다.
- **담긴 파일 목록과 파일별 SHA-256.** 「복사하라, 다시 쓰지 마라」를 지시가 아니라 **확인할 수
  있는 것**으로 만듭니다. 받는 쪽 Claude가 `SKILL.md`를 친절하게 다시 저장하면 값이 달라지고,
  그 자리에서 보입니다. 나중에 「스킬이 안 뜨는데요」로 알게 되지 않습니다.
- **설치 방법과 확인 방법.**

이 스킬이 없는 사람을 위해 쓰이므로 받는 쪽에는 아무것도 설치할 필요가 없습니다.
내용은 복사 목록이고, 받는 사람의 에이전트에게 무언가를 실행시키는 지시는 넣지 않습니다. 첨부
파일이 남의 에이전트를 조종하는 모양은 보내는 사람을 믿더라도 만들지 않는 편이 맞습니다.

거기 세 가지가 적혀 있습니다. 전부 **오류 없이 조용히 실패하는** 것들이라, 안 알려주면 「안
되는데요」라는 말만 돌아옵니다.

- **읽어서 새로 쓰지 말고 복사할 것.** 다시 저장하면 BOM이 붙어서 앞서 막은 고장이 마지막
  단계에서 되살아납니다. 해시 표로 대조하면 그 자리에서 잡힙니다
- **설치한 세션에서는 안 보인다는 것.** 스킬 목록은 세션이 시작될 때 읽힙니다
- **복사할 폴더를 헷갈리지 말 것.** 압축을 풀면 zip 이름을 딴 폴더가 하나 더 생기는데, 복사할
  것은 그 안쪽입니다. 바깥 것을 복사하면 경로가 한 겹 깊어져 스킬이 안 뜹니다

## 하지 않는 것

스킬을 만들거나 고치지 않습니다. 무엇을 보장하는 스킬을 만들 것인가는
[`link-skill-authoring`](../link-skill-authoring/README.md)이 다룹니다.

**폴더의 일부만 골라 담지 않습니다.** 제외 옵션이 없습니다. 있으면 zip이 폴더와 달라지고, 다음
사람이 같은 스킬을 포장할 때 다른 결과가 나옵니다. 뺄 것이 있으면 폴더에서 지우고 다시 돌리세요.

포장하는 쪽 컴퓨터에 아무것도 설치하지 않고, zip을 어디로 보내지도 않습니다. 지정한 경로에 파일 하나를 쓰고 끝냅니다.
스킬이 잘 만들어졌는지는 판단하지 않습니다. 옮기는 동안 깨지지 않는지만 봅니다.

## 필요한 것

파이썬. 표준 라이브러리만 씁니다.
